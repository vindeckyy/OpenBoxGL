# ADR 0102: 2.1 compatibility policy and scheduled removals

Status: Accepted (2026-11-01)

## Context

ADR 0087 says a minor release adds surface and announces deprecations but does not enforce them. ADR 0100 schedules removals in 2.1.0. Without a written exception the two policies would contradict each other, and every removal would be judged ad hoc.

## Decision

- A minor release may remove a surface only when **all** of the following hold:
  1. The surface was announced in a previous minor and is listed in `docs/api-deprecations.md`.
  2. The removal version is named in that ledger.
  3. The build returns a stable `410` problem document naming the replacement, or a documented CLI refusal.
  4. The release notes and the relevant upgrade guide explain the migration.
  5. The route/API ratchet records the removal in its retired ledger with a reason.
- 2.1.0 removes `/api/v1`, unversioned public `/api/*` dispatch, the legacy host names, and backup format 1 writes. It does **not** change state schema 7, backup format 2, plugin API 2, or sync format 3.
- A patch release still fixes defects only: no new surface, no format change, no migration.
- A format that makes the previous minor unable to read the data remains a major change, even when it migrates automatically.

## Consequences

- 2.1 is allowed to be a cleanup release without pretending it is additive-only.
- Clients get a replacement path in the error body rather than a bare 404.
- 2.0 can still read a 2.1 library because no required field changed.
