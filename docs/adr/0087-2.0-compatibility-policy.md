# ADR 0087: 2.0 compatibility and deprecation policy

Status: Accepted (2026-10-29)

## Context

OpenBox 1.19 accumulated compatibility scaffolding: `/api/v1` aliases, an unversioned public API, a flat `parity_*` import bridge, a one-file JSON state without an envelope, a v1 plugin protocol, and a backup archive without a format version. 2.0 has to change several of these. Without a written policy each change would be judged ad hoc.

## Decision

- **Major** (2.0.0): a change that needs user action, breaks a documented external contract, or makes data unreadable by the previous major line. Examples here: state schema v7, the `/api/v2` public surface, the host channel, backup format v2.
- **Minor** (2.1.0): additive routes, hooks, settings, and formats that the previous minor can ignore. Deprecations are announced but not enforced.
- **Patch** (2.0.1): fixes only. No new surface and no format change.
- A release that changes a format but migrates automatically and offers rollback is still major, because a downgrade is not transparent.
- Every deprecated surface is listed in `docs/api-deprecations.md` with an owner, an announcement version, and a removal version. `scripts/check_deprecations.py` enforces the rows (ADR 0099).
- Responses that can be affected by a format change advertise the contract versions through `GET /api/v2/version`.

## Consequences

- Contract changes are gated by ratchets (`scripts/check_api_contract.py`, `scripts/check_state_schema.py`), so drift fails review.
- Old clients keep working through the 2.0.x line only where a surface is listed as deprecated-but-served (ADR 0091).

## Verification
